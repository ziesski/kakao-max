# kakao-max 시작하기

Linux 서버의 데몬 하나가 카카오톡 계정을 유지하고, AI 클라이언트는 그 데몬에 연결합니다. 새 AI 대화를 열 때마다 계정에 다시 로그인하지 않습니다.

필요한 것: Node.js22.18 이상, npm, Git. 새 서버 설치에는 Linux/systemd와 sudo, 연결하는 컴퓨터에는 Node.js와 SSH가 필요합니다. AI 클라이언트는 MCP 도구와 사람 확인 창을 지원해야 합니다. 클라이언트가 확인 창을 막는 설정이면 서버가 이를 대신 승인하지 않습니다.

## 1. 서버에 처음 설치

Git 저장소를 받은 뒤 `main`의 깨끗한 체크아웃에서 실행합니다.

```bash
npm ci
npm run setup
```

`새 Linux 서버 설치`를 선택합니다. 마법사가 포트를 묻고 전용 서비스 계정을 만듭니다. 카카오 계정과 숨김 비밀번호를 입력하고, 휴대폰의 실제 인증 요청을 직접 승인합니다. 다른 PC가 사용 중이면 기본은 중단하며 자동으로 로그아웃하지 않습니다.

성공 후 자동 재로그인용 로그인 정보를 이 서버의 비공개 파일에 저장할지 선택합니다. 저장을 선택하면 기존 기기로 일반 재로그인만 허용하고 최대24시간3회로 제한합니다. 비밀번호 오류·계정 충돌·추가 인증 요구에는 멈춥니다. 저장하지 않는 선택도 지원합니다.

## 2. AI를 쓰는 컴퓨터에서 연결

그 컴퓨터에 kakao-max를 설치합니다. `npm install -g kakao-max`, macOS는 `brew install ziesski/tap/kakao-max`, Windows는 Scoop의 `ziesski/scoop-bucket`에서 설치할 수 있습니다([README](../README.md#getting-started)). 그다음 `kakao-max setup`(Git 체크아웃에서는 `npm run setup`)을 실행하고 `기존 데몬 연결`을 선택합니다. SSH 대상과 설치 때 선택한 서버 loopback 주소/포트를 입력합니다. SSH 대상은 `operator@server` 또는 자신의 SSH 별칭입니다. 공개 네트워크에 MCP 포트를 열 필요는 없습니다.

마법사가 연결을 진단하고 MCP 설정을 출력합니다. 출력한 설정을 AI 클라이언트가 지원하는 MCP 설정 형식에 등록합니다. 새 설정 키는 `kakao-max`이며 기존 사용자의 `kakaotalk` 키 설정도 그대로 계속 동작합니다. 클라이언트 설정은 허락 없이 덮어쓰지 않습니다.

새 설정은 로컬 Node 커넥터를 사용합니다. 이 커넥터가 SSH/TCP 연결만 복구하므로, 데몬이 재시작되어도 클라이언트 stdio를 유지합니다. MCP 초기화 이외의 작업·승인 응답은 자동 재실행하지 않습니다. 기존 `ssh -W` 직접 연결 설정은 다시 생성해야 이 동작을 사용할 수 있습니다.

## 3. 자연어로 작업하기

AI에 예를 들어 “프로젝트 방의 오늘 대화를 요약해서 결과방에 보내줘”라고 요청합니다.

- 방 제목·참여자·인원수로 찾습니다. 검색 페이지가 남아 있으면 이어 검색하고, 같은 이름의 방이 여러 개면 확인합니다.
- 대화 내용 조회와 읽음 표시, 발신은 별도 권한입니다. 처음 필요한 시점에 확인 창에서 허용합니다. 방을 읽을 때는 "이번만" 또는 "이 방은 앞으로 묻지 않고 읽기"를 고릅니다. 에이전트의 `confirm=true`는 승인이 아닙니다.
- 나와의 채팅은 묻지 않고 읽고 보내며, 내 메시지를 고치고 지울 수 있습니다. 메모나 시험용으로 씁니다.
- 처음 허용한 수신 방에는 설정된 한도 안에서 이후 일반 메시지·사진을 보낼 수 있습니다. 위험한 변경은 별도 확인을 유지합니다.
- 기록이 부족하면 그 범위를 보고합니다. 처음 등록한 기기가 오래된 모든 대화를 받는다고 보장하지 않습니다.

## 터미널에서 직접 대화하기

`npm run kakao -- chat`을 실행하면 왼쪽에서 방을 검색·선택하고, 오른쪽에서 최근 30개와 이벤트로 갱신되는 새 메시지를 보며 아래 입력창으로 답장할 수 있습니다. 조회와 전송은 기존 MCP의 ask/trust 정책을 따릅니다. 현재 모드는 화면에 표시하며, ask에서는 승인과 별개로 안읽은 방 제한이 적용됩니다. 메신저는 모드를 변경하거나 읽음 표시를 보내지 않습니다. [터미널 메신저 안내](runbooks/terminal-messenger.md)를 보세요.

녹화할 때는 `--demo --show-room "공개할 방 이름"`으로 다른 방 이름을 가리고 지정한 방만 여세요. 메시지 본문까지 익명화하지는 않습니다. 명령을 직접 입력하는 [대화형 셸](runbooks/cli-chat-shell.md)은 `npm run kakao -- shell`로 따로 실행할 수 있습니다.

## 같은 서버의 다른 사용자

MCP 포트는 서버 밖에서 접속할 수 없고(loopback), Linux에서는 허용한 OS 사용자의 연결만 받습니다. 설치 마법사가 `sudo`로 설치한 사람의 계정을 `KAKAO_MCP_ALLOWED_UIDS`에 기록하므로, 그 계정으로 들어오는 SSH 터널은 그대로 동작합니다. 다른 계정으로 연결하려면 그 계정의 uid(`id -u`)를 쉼표로 덧붙입니다. 데몬 자신의 계정과 root는 항상 허용합니다. 이전 버전으로 설치한 서버는 업데이트 전에 이 줄을 추가해야 하며, 없으면 업데이트가 데몬을 멈추기 전에 알리고 중단합니다.

**macOS·Windows에는 이 확인이 없습니다.** 데몬을 TCP(`127.0.0.1:PORT`)로 열면 그 컴퓨터의 모든 OS 사용자와 프로그램이 접속해 계정을 쓸 수 있고, 클라이언트 확인 창에 스스로 답할 수도 있습니다. 데몬은 시작할 때 이 경고를 출력합니다. 나만 쓰는 컴퓨터에서만 실행하세요. macOS에서는 TCP 대신 나만 접근할 수 있는 폴더(권한 0700)의 Unix 소켓(`KAKAO_MCP_LISTEN=/경로/kakao-max.sock`)을 쓰면 다른 사용자를 막을 수 있습니다. Windows는 Unix 소켓을 지원하지 않으므로 공용·다중 사용자 PC에서는 실행하지 마세요.

## AI 클라이언트 호환

승인은 클라이언트의 확인 창으로 받습니다. 확인 창이 없거나 스스로 거절하는 클라이언트에서는 승인이 필요한 작업이 거절되며, 서버는 이를 사람의 거절과 구분하지 못합니다.

| 클라이언트 | 확인 창 | 확인 |
|---|---|---|
| Claude Code 터미널(CLI) 2.1.308 | 표시하고 코드 입력으로 승인 | ✅ 2026-10-25 실계정 |
| Claude 데스크톱 앱 Code 탭 | 창 없이 자동 거절 | ✅ 2026-10-25 실계정 (승인 필요 작업 불가) |
| kakao-max 웹 화면(`apps/web`) | 브라우저에 표시하고 코드 입력으로 승인 | 🟡 fixture 데몬·브라우저 (실계정 미확인) |
| 그 밖의 클라이언트 | 미확인 | ❓ |

확인 창 없이 쓰려면 패스키 승인 페이지를 설정합니다.

## 웹 화면으로 쓰기 (내 컴퓨터)

`apps/web`은 실행 중인 데몬에 붙는 로컬 웹 화면입니다. AI 에이전트가 쓰는 계정을 사람이 보고 통제하는 제어판이며(공식 PC 카카오톡이 없는 리눅스 데스크톱에서도 쓸 수 있습니다), 여기서 직접 대화할 수도 있습니다. 카카오톡 전체 기능을 대신하는 앱은 아닙니다. 계정에 직접 로그인하지 않고, 설정·로그인 정보 파일도 읽지 않으며, 모든 조회·발신은 데몬의 MCP 도구와 권한·승인을 그대로 거칩니다. 공개 웹 서비스가 아니라 내 컴퓨터의 브라우저에서만 쓰는 화면입니다.

```bash
npm run web
```

터미널에 출력되는 실행 링크(`http://127.0.0.1:8899/launch?t=…`)를 브라우저에서 엽니다. 이 링크는 실행할 때마다 새로 만들어지며, 링크를 가진 사람은 이 화면으로 내 계정을 쓸 수 있으니 공유하지 마세요. 화면이 브라우저를 대신 열지 않는 것도 같은 이유입니다(다른 프로그램에 링크를 넘기면 같은 컴퓨터의 다른 사용자가 프로세스 목록에서 볼 수 있습니다). 기본으로 같은 컴퓨터의 `127.0.0.1:8787` 데몬에 연결하며, 다른 주소는 `--listen 127.0.0.1:9787` 또는 `MCP_HOST`/`MCP_PORT`, 화면 포트는 `PORT`로 바꿉니다.

데몬이 서버에 있으면 SSH 대상을 함께 줍니다. 별도 터널을 열 필요가 없습니다.

```bash
npm run web -- --ssh operator@server
```

MCP 커넥터와 같은 방식(`ssh -W 127.0.0.1:8787`)으로 서버의 루프백 데몬에 붙습니다. 서버에서 명령을 실행하지 않고 내 컴퓨터에 터널 포트도 열지 않습니다. 대상은 SSH 별칭이나 `user@host`만 받으며, 비밀번호 질문 없이 접속되는 키·에이전트 설정이 필요합니다(`BatchMode`). 서버의 데몬 포트가 다르면 `--listen 127.0.0.1:<포트>`를 함께 줍니다. 연결이 끊기면 화면이 다시 연결합니다.

- 설정 탭의 "에이전트 제어"에서 데몬·계정 연결, 에이전트 모드(ask/trust, 표시만 — 바꾸려면 운영자가 `npm run setup -- --mode`), 일시정지 상태, 대기 중인 승인, 허용한 권한 목록을 봅니다. "일시정지"는 에이전트의 전송·계정 변경을 즉시 멈춥니다. "해제 요청"은 데몬의 확인 창을 띄우며, 표시된 코드를 직접 입력해야 풀립니다. 권한마다 있는 "철회"는 즉시 적용되고, 다시 허용하려면 승인이 필요합니다.
- 보내기·삭제·전달·나가기·읽음 표시는 작업마다 하나의 `requestId`를 화면이 정해 끝까지 유지합니다. 처리 도중 연결이 끊기거나 시간이 초과되는 등 결과를 알 수 없으면 "결과 불명"으로 표시하고 메시지를 지우지 않습니다. 실제로 갔는지 휴대폰에서 먼저 확인하세요. "같은 요청으로 다시 확인"(또는 같은 내용을 다시 보내기)은 같은 `requestId`로 데몬에 다시 묻기 때문에 두 번 보내지지 않습니다.

- 방 나가기·읽음 표시·전달·나에게서만 삭제·친구 검색은 선택 도구 그룹이 필요합니다. 데몬 설정에 `KAKAO_MCP_TOOL_GROUPS=chats,friends`를 둡니다.
- 웹 화면에서 닫힌 방을 열거나 처음 보내는 방에 보내면 데몬의 확인 창이 브라우저에 뜹니다. 창에 표시된 확인 코드를 직접 입력해야 승인되며, 화면이 코드를 대신 채우지 않습니다. "앞으로 묻지 않기"를 고르면 그 방의 이후 조회나 전송은 묻지 않습니다(`list_permissions`에서 확인, `revoke_permission`으로 철회). 거절하면 그 작업은 취소되고, 닫거나 약 110초 동안 답하지 않으면 아무것도 하지 않습니다.
- 열려 있는 웹 화면이 없으면 확인 창은 바로 취소됩니다. 에이전트가 요청한 작업의 확인 창은 이 화면이 아니라 에이전트를 실행한 클라이언트에 뜹니다.
- 데몬의 클라이언트 확인 창을 끈 경우(`KAKAO_APPROVAL_CLIENT_CONFIRM=off`)에는 승인이 필요한 작업이 거절되고, 패스키 승인 페이지가 설정돼 있으면 오류와 함께 승인 링크를 보여 줍니다. 실패한 메시지는 보낸 것처럼 표시하지 않고 입력창에 되돌립니다.
- 화면 서버는 `127.0.0.1`에만 열리고, 이 화면 자신의 페이지만 API를 쓸 수 있습니다. 다른 웹사이트의 요청(CSRF·DNS rebinding·교차 사이트 이미지)은 거절합니다. 메시지 속 링크 미리보기는 공개 주소만 가져오며, 리디렉션도 매번 다시 확인합니다.
- 실행 링크로 연 브라우저만 화면과 API를 쓸 수 있습니다. 같은 컴퓨터의 다른 OS 사용자나 프로그램이 `127.0.0.1:8899`에 접속해도 링크의 비밀값이 없으면 거절됩니다. 화면 서버를 다시 시작하면 새 링크로 다시 엽니다.
- 받은 이모티콘은 그림 대신 😀와 이모티콘 이름으로 표시합니다.
- 대화 백업 복원은 지원하지 않습니다.

검증 범위: 실제 MCP 서버·도구 정의에 가짜 계정을 붙인 fixture에서 조회·발신·삭제·전달·나가기·승인 거절과 Windows 브라우저 화면을 확인했습니다🟡. 제어판(일시정지·해제 승인·권한 철회)과 결과 불명 표시는 fixture 데몬과 브라우저에서, `--ssh`는 가짜 ssh 프로세스로만 확인했습니다🟡. 실계정 연결과 실제 SSH 서버 연결은 아직 확인하지 않았습니다❓.

## 연결이나 로그인이 실패하면

연결한 컴퓨터에서 같은 주소/SSH 설정으로 진단합니다.

```bash
npm run setup -- --doctor --ssh operator@server --listen 127.0.0.1:8787
```

설치 포트가 다르면 그 값을 사용합니다. 진단은 계정 ID·대화·비밀번호를 출력하지 않고, 로그인·재시작·전송도 하지 않습니다.

관리형 설치의 계정 인증을 고치려면 서버의 깨끗한 최신 `main`에서 실행합니다.

```bash
npm run setup -- --repair
```

기존 기기와 계정 ID를 유지하며, 로그인 정보는 터미널에서 숨김 입력으로 수정합니다. 이메일·비밀번호의 문자 인코딩만 깨졌다면 다시 입력할 수 있고, 기기 키·토큰 등 다른 값의 손상은 임의로 복구하지 않습니다. 자동 로그인이 중단된 경우 정보를 수정한 뒤 사람이 명시적으로 횟수 제한을 초기화할 수 있습니다. 동작 중인 서비스·다른 프로세스가 있거나 operator pause가 설정돼 있으면 강제로 중지하지 않습니다. 새 기기 등록·강제 로그인은 복구 경로에 없습니다.

전송 도중 연결이 끊겼다면 같은 `requestId`의 작업 상태부터 확인합니다. 새 ID로 다시 보내지 않습니다. 이때 재연결은 전송 성공/실패를 대신 판정하지 않습니다.
